- **PACE 3 decisions (2026-11-18, change only if the user asks; the two defaults proposed in chat were accepted by continuing):** (1) **each sync run = PULL, THEN PUSH.** Pull runs on the first run (sign-in), when forced by `sync({ pull: true })` (ServicesProvider does this whenever `online` becomes true), and otherwise at most every **5 minutes** (`DEFAULT_PULL_INTERVAL_MS`); the 20 s sweep only pushes in between (pull = Firestore reads, push is cheap). Pulling first means a pending local edit that is newer than the cloud copy is kept and wins the push, an older one loses. (2) **Cursor = server time, not `updatedAt`:** every push writes `syncedAt: serverTimestamp()`; pulls ask `syncedAt > cursor`. Reason: `updatedAt` is the device's clock — a device that edits offline and pushes days later would be older than every other device's cursor and never be pulled. The cursor is whole ms, so the newest document is re-read by the next pull (harmless, one read per collection per pull). `syncedAt` never leaves the adapter (`fromRemote`). (3) **Cursor lives in the user's own IndexedDB database** (`syncMetadata` store, key `cursor:<collection>`, via `IndexedDBCursorStore`), not localStorage: wiping local data also wipes the cursor, so the next pull refills it. Demo mode uses `MemoryCursorStore`. (4) **`Repository.applyRemote(remote)`** stores a backend record as `synced` with NO `touch()`/version bump; last-write-wins by `updatedAt` (outcomes `created`/`updated`/`unchanged`/`kept-local`); rejects a record with no `id`/`updatedAt` as `INVALID` (SyncService skips and counts those in `pullSkipped` so one bad document can't block the rest; a storage error instead stops that collection and keeps the old cursor). (5) **Push conflicts are now resolved on the spot:** the winning `remote` replaces the local record and is marked synced (counted in `conflicts` and `resolved`), so it is no longer re-reported every sweep. (6) **Bug fixed on the way:** `SyncService` used to mark a record synced after a push even if the user edited it while the push was in flight (that edit then never pushed). `Repository.setSyncStatus(id, status, { ifUpdatedAt })` now leaves such a record pending. (7) **Adapter `pull()` is optional** (`ADAPTER_METHODS` is still just `push`), so an adapter without it is simply never pulled. (8) `createServices` options `syncCursors` / `syncPullIntervalMs`; `SyncService` option `onPulled({ collection: count })` — `createServices` uses it to call `reminders.sync()` when schedules/occurrences arrived from another device.
- **Known limits after PACE 3 (not bugs, scheduled for PACE 4 or later):** (a) FIXED in PACE 4 for the Scheduler (other screens as they are built); (b) an edit made in the few ms between `applyRemote` reading a local record and writing it can be overwritten by the incoming newer record (the same last-write-wins outcome, at worst a few ms early); (c) the first pull of a very large account reads everything in one query (no paging) — fine for a student's data volume; (d) Firestore free-tier reads: ≈ 7 queries per pull (one per collection) every 5 min while the app is open, plus the one re-read document each.
