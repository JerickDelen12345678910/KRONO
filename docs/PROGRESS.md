- **PACE 2 decisions (2026-11-18, change only if the user asks):** (1) **layout = per-user subcollections** `users/{uid}/{collection}/{record.id}` — matches `MemoryAdapter`'s `users/${userId}/${col}` namespacing, PROJECT_PLAN, and the existing owner-only `users/{uid}/…` rule, so no `userId` field is stored on documents; the collection name is the key from `createRepositories()` (schedules, occurrences, academicPeriods, subjects, workouts, exerciseHistory, destinations). (2) **one transaction per record** (read remote → write only if remote `updatedAt` is not newer), up to 5 in flight per `push()`; equal `updatedAt` counts as applied so retries are idempotent. (3) **stored copy = the record as plain JSON minus `syncStatus`** (device-local state; `undefined` fields are dropped because Firestore rejects them). (4) **contract extended with a per-record `{ id, status: 'error', error }` result** (`SYNC_RESULT.ERROR`): one bad record can no longer block the rest of its batch; `SyncService` marks the run `ok: false`, sets `lastError`, and leaves that record pending for the next sweep. `push()` still rejects only when the whole call can't start — offline (`ERROR_CODE.OFFLINE`, checked via `navigator.onLine` so it fails fast instead of waiting on a transaction timeout). (5) **after `dispose()`, `push()` returns `[]`** instead of fake "applied" results, so a disposed adapter can never cause records to be marked synced. (6) the adapter never imports the Firebase SDK or `lib/firebase.js` (which needs Vite's `import.meta.env`): `ServicesProvider` passes `{ db, doc, runTransaction }`, so `check-sync.mjs` tests the whole last-write-wins logic against a fake Firestore in Node.
- **`firestore.rules` (PACE 2):** the old wildcard `match /{document=**}` under `users/{uid}` is replaced by an explicit `match /{col}/{id}` that allows read/delete for the owner and create/update only for the whitelisted synced collections when the document has `id == document id`, string `updatedAt`, integer `version`, boolean `deleted`. Profile rules and the final deny-all are unchanged. Last-write-wins is NOT enforced in the rules — the client transaction does it atomically. **The rules could not be run here** (no Firebase emulator); test them with the Rules Playground or the real-project check above. A new synced collection must be added to `isSyncedCollection()` or its pushes are denied.
- **Risks to watch in the real-project check (can't be tested without the real backend):** (a) Firestore rejects **nested arrays** (an array directly inside an array); if a model (schedule/workout) has one, that collection's records will come back as `error` results with the cause in `SyncService.lastError` — fix by flattening that field; (b) any record written to a real user's IndexedDB while PACE 1's fake adapter was active was marked `synced` without ever reaching a real cloud. If you used real sign-in during that window, edit those records once (that resets them to `pending`) or delete IndexedDB `local-data_<uid>` in DevTools → Application so they re-queue.
- **PACE 1 scope still deliberately stops short of full conflict resolution:** when `push()` reports a `conflict`, `SyncService` counts it and leaves the local record pending — it does NOT yet pull the winning remote record into local storage (needs the pull direction, PACE 3). Until then a conflicting record is re-checked every ~20 s sweep, harmlessly (nothing is lost, corrupted or duplicated).
- **Two product/architecture decisions were made for Phase 7, per docs/PROJECT_PLAN.md §5's requirement to "define a conflict policy before implementation" (decided 2026-11-17, change only if the user asks):** (1) **conflict policy = last-write-wins by `updatedAt`** — no manual merge UI, matching that nothing like that exists anywhere in `docs/DESIGN_LOCK.md` or the design preview; (2) **queue design = reuse the existing `syncStatus` field** per record rather than a separate operation-log collection — `Repository.listUnsynced()` already existed for exactly this (built in Phase 3 PACE 2, "used by Phase 7"), and `touch()`/`markDeleted()` in `models/common.js` already reset `syncStatus` away from `synced` on every edit/delete, so the queue needed no new code at all, just a consumer.
- SyncService triggers (decided 2026-11-17): (1) once implicitly whenever anything calls `services.sync.sync()`; (2) a periodic sweep every 20 seconds (`DEFAULT_INTERVAL_MS` in `SyncService.js`), chosen as a reasonable default rather than asked about, since it's an implementation detail rather than a product decision — tell me if you want it tuned; (3) a `useEffect` in `ServicesProvider.jsx` that calls `sync()` whenever `online` (from `useAuth()`, backed by `useOnlineStatus.js`) becomes true. Deliberately NOT wired through each service's own `onChange` hook the way reminders are — that pattern only exists on `ScheduleService` today, and wiring it into `WorkoutService`/`PlaceService`/etc. too would mean guessing at files not yet seen; the periodic sweep already catches every repository's pending records regardless of which service wrote them, without needing that.
- `SyncService` is generic: it iterates whatever's in the `repos` map passed to it (currently `schedules`, `occurrences`, `academicPeriods`, `subjects`, `workouts`, `exerciseHistory`, `destinations` — exactly `createRepositories()`'s output) and calls `listUnsynced()`/`setSyncStatus()` on each, so any future collection added to `createRepositories()` is picked up automatically with no `SyncService` change needed.
- `createDefaultSyncAdapter({ userId, demo, firestore })` (in `src/sync/index.js`) returns `FirestoreSyncAdapter` only when `!demo`, a `userId` is given and a Firestore instance is passed; otherwise `MemorySyncAdapter` (demo mode, or no `.env`).
