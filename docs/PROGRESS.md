(3) **stored copy = the record as plain JSON minus `syncStatus`** (device-local state; `undefined` fields are dropped because Firestore rejects them). (4) **contract extended with a per-record `{ id, status: 'error', error }` result** (`SYNC_RESULT.ERROR`): one bad record can no longer block the rest of its batch; `SyncService` marks the run `ok: false`, sets `lastError`, and leaves that record pending for the next sweep. `push()` still rejects only when the whole call can't start — offline (`ERROR_CODE.OFFLINE`, checked via `navigator.onLine` so it fails fast instead of waiting on a transaction timeout). (5) **after `dispose()`, `push()` returns `[]`** instead of fake "applied" results, so a disposed adapter can never cause records to be marked synced. - **PACE 3 decisions (2026-11-18, change only if the user asks; the two defaults proposed in chat were accepted by continuing):** (1) **each sync run = PULL, THEN PUSH.** Pull runs on the first run (sign-in), when forced by `sync({ pull: true })` (ServicesProvider does this whenever `online` becomes true), and otherwise at most every **5 minutes** (`DEFAULT_PULL_INTERVAL_MS`); the 20 s sweep only pushes in between (pull = Firestore reads, push is cheap). Pulling first means a pending local edit that is newer than the cloud copy is kept and wins the push, an older one loses. (2) **Cursor = server time, not `updatedAt`:** every push writes `syncedAt: serverTimestamp()`; pulls ask `syncedAt > cursor`. Reason: `updatedAt` is the device's clock — a device that edits offline and pushes days later would be older than every other device's cursor and never be pulled. The cursor is whole ms, so the newest document is re-read by the next pull (harmless, one read per collection per pull). `syncedAt` never leaves the adapter (`fromRemote`). (3) **Cursor lives in the user's own IndexedDB database** (`syncMetadata` store, key `cursor:<collection>`, via `IndexedDBCursorStore`), not localStorage: wiping local data also wipes the cursor, so the next pull refills it. Demo mode uses `MemoryCursorStore`. (4) **`Repository.applyRemote(remote)`** stores a backend record as `synced` with NO `touch()`/version bump; last-write-wins by `updatedAt` (outcomes `created`/`updated`/`unchanged`/`kept-local`); rejects a record with no `id`/`updatedAt` as `INVALID` (SyncService skips and counts those in `pullSkipped` so one bad document can't block the rest; a storage error instead stops that collection and keeps the old cursor). (5) **Push conflicts are now resolved on the spot:** the winning `remote` replaces the local record and is marked synced (counted in `conflicts` and `resolved`), so it is no longer re-reported every sweep. (6) **Bug fixed on the way:** `SyncService` used to mark a record synced after a push even if the user edited it while the push was in flight (that edit then never pushed). `Repository.setSyncStatus(id, status, { ifUpdatedAt })` now leaves such a record pending. (7) **Adapter `pull()` is optional** (`ADAPTER_METHODS` is still just `push`), so an adapter without it is simply never pulled. (8) `createServices` options `syncCursors` / `syncPullIntervalMs`; `SyncService` option `onPulled({ collection: count })` — `createServices` uses it to call `reminders.sync()` when schedules/occurrences arrived from another device.
- **Known limits after PACE 3 (not bugs, scheduled for PACE 4 or later):** (a) FIXED in PACE 4 for the Scheduler (other screens as they are built); (b) an edit made in the few ms between `applyRemote` reading a local record and writing it can be overwritten by the incoming newer record (the same last-write-wins outcome, at worst a few ms early); (c) the first pull of a very large account reads everything in one query (no paging) — fine for a student's data volume; (d) Firestore free-tier reads: ≈ 7 queries per pull (one per collection) every 5 min while the app is open, plus the one re-read document each.
- **Two product/architecture decisions were made for Phase 7, per docs/PROJECT_PLAN.md §5's requirement to "define a conflict policy before implementation" (decided 2026-11-17, change only if the user asks):** (1) **conflict policy = last-write-wins by `updatedAt`** — no manual merge UI, matching that nothing like that exists anywhere in `docs/DESIGN_LOCK.md` or the design preview; (2) **queue design = reuse the existing `syncStatus` field** per record rather than a separate operation-log collection — `Repository.listUnsynced()` already existed for exactly this (built in Phase 3 PACE 2, "used by Phase 7"), and `touch()`/`markDeleted()` in `models/common.js` already reset `syncStatus` away from `synced` on every edit/delete, so the queue needed no new code at all, just a consumer.
- SyncService triggers (decided 2026-11-17; PACE 3 added pull triggers, see the PACE 3 decisions above): (1) once implicitly whenever anything calls `services.sync.sync()`; (2) a periodic sweep every 20 seconds (`DEFAULT_INTERVAL_MS` in `SyncService.js`), chosen as a reasonable default rather than asked about, since it's an implementation detail rather than a product decision — tell me if you want it tuned; (3) a `useEffect` in `ServicesProvider.jsx` that calls `sync()` whenever `online` (from `useAuth()`, backed by `useOnlineStatus.js`) becomes true. Deliberately NOT wired through each service's own `onChange` hook the way reminders are — that pattern only exists on `ScheduleService` today, and wiring it into `WorkoutService`/`PlaceService`/etc. too would mean guessing at files not yet seen; the periodic sweep already catches every repository's pending records regardless of which service wrote them, without needing that.
- `SyncService` is generic: it iterates whatever's in the `repos` map passed to it (currently `schedules`, `occurrences`, `academicPeriods`, `subjects`, `workouts`, `exerciseHistory`, `destinations` — exactly `createRepositories()`'s output) and calls `listUnsynced()`/`setSyncStatus()` on each, so any future collection added to `createRepositories()` is picked up automatically with no `SyncService` change needed.
